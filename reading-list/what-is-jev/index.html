Jev는 무엇이고 지금 써야 하는가

교육팀 조사2026. 09. 22.공개 7일 차 기준

TypeSafe AI가 2026년 9월 15일 얼리액세스로 공개한 Jev는 글을 쓰지 않고 타입이 정해진 판정만 돌려주는 모델입니다. 회사는 홈페이지에 193.6배 빠르고 444.6배 저렴하다고 내걸었지만 이는 전부 자사 평가에서 나온 값이고, 공개 일주일 사이에 나온 독립 측정값은 속도 1.4~5.4배, 비용 2.7~30배였습니다. 더 싸고 빠른 것은 맞지만, 회사가 내건 배수와는 수십 배 차이가 납니다. 게다가 이 모델을 새로운 범주로 볼 유일한 근거였던 확률 보정이 독립 측정에서 가장 나쁘게 나왔습니다.

결론부터 적습니다. 정답을 붙여 둔 데이터가 있으면 작은 분류기를 직접 학습시키는 쪽이 모든 면에서 낫고, 이미 LLM을 부르고 있으면 정해진 형식으로 답을 받는 지금 방식(structured outputs)을 그대로 두는 편이 낫습니다. Jev를 쓸 값어치가 있는 경우는 네 조건이 한꺼번에 맞을 때뿐입니다. 학습에 쓸 정답 데이터가 없고, 물어볼 것이 실행 중에 바뀌고, 한 건을 두고 물을 것이 여럿이고, 응답 시간 상한이 실제로 걸려 있을 때입니다.

쉬운 설명

보통 쓰는 LLM은 물어보면 글로 답하는 상대입니다. Jev는 글을 아예 못 씁니다. 대신 세 가지로만 답합니다. 예인지 아니오인지, 주어진 목록에서 무엇을 고를지, 몇 점인지입니다. 근거도 설명도 돌려주지 않습니다.

그 대가로 빠르고 쌉니다. 그리고 답할 때마다 "저는 이만큼 확신합니다"라는 숫자를 같이 줍니다. 이 숫자가 Jev를 특별하게 만들어 줄 유일한 부분이었는데, 남들이 재 보니 부풀려져 있었습니다. 90% 확신한다고 말한 답이 실제로는 80%만 맞는 식입니다.

이것이 왜 문제인지는 회사가 권하는 사용법을 보면 바로 드러납니다. "확신이 높으면 사람 확인 없이 자동 처리"가 권장 패턴인데, 모델이 실제보다 확신을 부풀린다면 사람이 봤어야 할 건을 정확히 골라서 자동으로 통과시키게 됩니다.

한 번 주고받는 모습

말로만 들으면 감이 안 오므로 실제 오가는 모양을 봅니다. 고객 문의 한 건을 분류한다고 해 보겠습니다. 보내는 쪽은 판단할 대상(state)과 이름 붙인 질문들을 함께 실어 보냅니다. 아래는 공개된 API 규격에 맞춰 적은 것입니다.

요청

{
  "model": "jev-latest",
  "state": { "ticket": "사파리에서 내보내기 버튼을 누르면 창이 닫힙니다. 크롬에서는 됩니다." },
  "questions": {
    "category": {
      "type": "choice",
      "instructions": "어떤 종류의 문의인가?",
      "criteria": {
        "bug_report": "무언가 고장났다",
        "feature_request": "새 기능을 요청한다",
        "billing": "결제나 환불 문제다"
      }
    },
    "severity": {
      "type": "score",
      "instructions": "얼마나 심각한가?",
      "criteria": [
        "겉모습 문제, 사용에 지장 없음",
        "기능이 나빠졌으나 우회 방법 있음",
        "막혀서 진행 불가, 우회 방법 없음"
      ]
    },
    "has_repro": { "type": "noul", "instructions": "재현 절차가 들어 있는가?" }
  }
}

응답

{
  "model": "jev-1.13.0",
  "answers": {
    "category": {
      "type": "choice",
      "choice": "bug_report",
      "probabilities": { "bug_report": 0.84, "feature_request": 0.15, "billing": 0.01 },
      "confidence": 0.6
    },
    "severity": {
      "type": "score",
      "score": 1.3,
      "probabilities": { "0": 0.0, "1": 0.7, "2": 0.3 },
      "confidence": 0.54
    },
    "has_repro": { "type": "noul", "noul": 0.93 }
  },
  "usage": { "input_tokens": 210, "output_tokens": 31 }
}

여기서 읽어야 할 것이 넷입니다.

  • 질문 셋이 한 번에 처리됩니다. 순서대로 답을 만들어 내는 것이 아니라 한 번의 연산으로 세 답이 동시에 나옵니다. 그래서 질문을 서른 개 붙여도 걸리는 시간이 하나일 때와 거의 같습니다. 이것이 앞에서 말한 비용 이점의 정체입니다.
  • 심각도 1.3은 "1.3단계"가 아닙니다. 0단계 0%, 1단계 70%, 2단계 30%를 가중평균한 값입니다. 즉 이 모델은 한 단계를 고른 것이 아니라 단계별 확률을 내놓았고, 1.3은 그 분포를 숫자 하나로 접은 것입니다. 2단계 확률이 30%나 된다는 사실이 평균값에는 안 보이므로, 자동 처리 기준을 세울 때는 평균이 아니라 분포를 봐야 합니다.
  • confidence는 따로 예측한 값이 아닙니다. 바로 위 probabilities에서 계산해 낸 값입니다. TypeSafe 문서는 선택지가 셋일 때 (3 × 최대확률 − 1) / 2라고 적어 두었는데, 이 예시의 0.84를 넣으면 0.76이 나와 응답에 적힌 0.6과 맞지 않습니다. 공식과 예시의 출처가 달라 생긴 불일치로 보이며 저희가 확인하지는 못했습니다. 다만 요점은 그대로입니다. 분포를 이미 받았으니 confidence에 추가 정보는 없고, 필요하면 직접 계산해 쓰면 됩니다.
  • 근거가 없습니다. 왜 bug_report인지, 어느 문장을 보고 재현 절차가 있다고 판단했는지는 돌려주지 않습니다. 오답이 나왔을 때 손에 쥐는 단서는 확률 분포뿐이고, 고칠 수 있는 것은 criteria에 적은 기준 문장뿐입니다.

그리고 이 요청이 바로 뒤에서 이야기할 "질문 분해"의 실물입니다. "이 문의를 어떻게 처리할까?"라고 한 번에 묻는 대신 종류·심각도·재현 여부 셋으로 쪼개 물었습니다. 중요한 것은 이 쪼개기 자체는 Jev가 아니어도 할 수 있다는 점입니다. 같은 세 질문을 지금 쓰는 LLM에 정해진 형식으로 물어도 됩니다. Jev가 주는 것은 쪼개기라는 발상이 아니라 그것을 싸고 빠르게 처리하는 방식입니다.

쓸 자리와 쓰지 말 자리

기계적으로 Jev는 엔드포인트 하나입니다. 평가할 대상인 상태와 이름 붙인 질문 목록을 보내면, 예/아니오 확률(Noul), 선택지별 확률(Choice), 채점 기준에 따른 점수(Score) 셋 중 하나로 답이 옵니다. 이미지도 소리도 받지 않고, 파인튜닝도 없습니다. 도메인에 맞추는 수단은 질문에 적는 기준 문장이 전부입니다.

  • 라벨 1,000건을 모을 수 있고 분류 체계가 고정되어 있다면 작은 인코더를 직접 학습시키십시오. Banking77 독립 측정에서 파라미터 2,200만 개짜리 인코더와 로지스틱 회귀 조합이 정확도 93.2%에 CPU 8ms였고, 같은 과제에서 학습 없이 바로 답하는(zero-shot) Jev는 80.1%에 약 150ms였습니다. 13퍼센트포인트 차이에 19배 지연 차이, 거기에 호출당 요금까지 붙습니다.
  • 입력이 금액이나 날짜나 개수 같은 숫자라면 그래디언트 부스팅 트리를 쓸 자리입니다. TypeSafe 자사 문서도 Jev가 계산기가 아니고 날짜를 순서 있는 수량이 아니라 텍스트로 읽는다고 적어 두었습니다. 다만 사전 등록 방식으로 5,721회를 호출한 한 독립 시험은 숫자 비교와 날짜 정렬에서 99.6%를 측정하고 자사 문서가 오히려 모델을 과소평가한다고 결론지었습니다. 이 불일치는 아직 해소되지 않았습니다.
  • 물량이 적고 이미 LLM 호출 흐름 안이라면 그대로 두십시오. 가장 싼 구조화 출력 LLM 대비 비용 우위가 2.7배뿐이라, 새 벤더와 새 SDK를, 그리고 들여다볼 수 없는 구간을 하나 더 떠안을 만한 이득이 아닙니다.

Jev가 이기는 자리는 하나입니다. 판단할 대상을 한 번만 보내고 질문을 여러 개 붙여 한꺼번에 답받는 구조(fan-out)입니다. 질문 30개를 묶은 호출의 벽시계 시간이 질문 1개와 같은 약 150ms였고, 선택지가 2개에서 255개로 늘어도 지연이 평평하게 유지되는 것이 독립 확인되었습니다. 반대로 호출당 질문 하나 패턴을 쓰면 고정 지연만 부담하고 이득은 하나도 얻지 못합니다.

제약도 미리 알아야 합니다. 선택지는 255개가 상한이고 256개부터는 오류로 끊깁니다. 컨텍스트 한도는 출처마다 다르게 적혀 있습니다. 그리고 보안상 중요한 것 하나. TypeSafe는 Jev가 주입된 지시문에 조종될 수 있고 입력을 기본적으로 적대적인 것으로 취급하지 않는다고 문서에 적어 두었습니다. 그러면서 공개한 예제 목록에는 "LLM 가드레일"이 들어 있습니다. Jev로 만든 가드레일은 그 자체가 프롬프트 주입 대상이므로 단독 보안 경계로 쓰면 안 됩니다.

자사 수치와 독립 측정의 거리

TypeSafe의 모든 배수는 자사가 만든 워크플로 평가 네 종에서 나옵니다. 이 평가에서 "정확도"로 표기된 값은 정답과의 일치가 아니라 GPT-6 Astra와 Claude Fable 5.1의 응답을 평균낸 것과 얼마나 합치하는가입니다. 정답지가 아니라 다른 모델의 의견입니다. TypeSafe도 이 기준이 두 회사 쪽으로 답을 편향시킨다고 인정했습니다. 구조상 Jev가 기준 모델보다 더 맞혀서 점수를 올리는 일은 불가능하고, 더 많이 동의해야만 점수가 오릅니다.

그 표 안에서도 Jev는 최상위가 아닙니다. 합치도 67.8%로 Claude Opus 5의 73.1%와 Sol의 74.1%보다 낮습니다. 지연 측정 환경 공개는 한 문장이 전부입니다. "우리 평가는 대체로 서부 해안에 있는 우리 노트북에서 실행한다."

정리하면 더 싸고 빠르다는 방향은 독립 측정에서도 확인됐고, 배수는 확인되지 않았습니다. 기준선을 함께 돌린 독립 시험은 모두 Jev가 더 싸고 빠르다고 보고했지만, 193.6배 근처를 재현한 곳은 한 곳도 없습니다. 헤드라인 배수가 자사 표에서 가장 느리고 가장 비싼 구성을 상대로 뽑은 값이니 당연한 결과입니다. 지연은 측정 환경에 따라 10배까지 벌어져 있으므로, 70ms를 최선의 경우로 보고 약 400ms를 현실적 하한으로 잡은 뒤 자기 환경에서 직접 재야 합니다.

비용 주장은 속도 주장보다 훨씬 잘 버팁니다. 출력 토큰이 무료라 쓰기 전에 비용을 정확히 계산할 수 있다는 점도 실제 장점입니다. 다만 "효율적"이라는 말이 정가 기준 달러만 뜻한다는 점은 분명히 해야 합니다. 에너지나 연산량 측정은 자사 자료에도 독립 출처에도 없습니다.

모델이 아니라 질문 분해의 몫

출시 후 나온 독립 측정 가운데 가장 날카로운 결과가 여기 있습니다. 피싱 메일 2,000건을 놓고 "이것은 피싱인가"라는 질문 하나로 물었을 때 Jev는 62.6%, Claude Haiku 4.5는 81.3%였습니다. Jev가 크게 졌습니다.

그다음 같은 판정을 타입이 붙은 질문 다섯 개로 쪼개자 Jev가 95.0%로 올라 Haiku의 93.2%를 넘었습니다. 그런데 여기에 조건이 둘 붙습니다. 95.0%는 라벨 1,000건으로 학습한 로지스틱 회귀를 위에 얹어야 나온 값이고, 두 모델의 격차는 통계적으로 유의하지 않습니다.

이 효과는 TypeSafe 자사 평가 표 안에서도 그대로 보입니다. 같은 모델을 단일 프롬프트로 물었을 때와 분해된 질문으로 물었을 때를 나란히 실어 두었는데, 분해만으로 생기는 점프가 Jev와 기준선 사이의 격차보다 큽니다.

Haiku 4.5는 질문을 쪼개는 것만으로 35.5퍼센트포인트가 올랐습니다. 그리고 분해를 적용한 뒤의 Jev 67.8%는 Terra의 67.9%와 사실상 동률입니다. TypeSafe가 기준선의 분해 결과까지 함께 공개한 것은 공정한 처사이고 그 점은 인정해야 합니다. 다만 그 공정한 표가 말해 주는 내용도 함께 읽어야 합니다. 분해는 어느 모델에나 통하는 방법이고, 그것을 적용하고 나면 Jev의 지능 우위는 사라지고 비용과 지연 우위만 남습니다.

교육팀에게 이것은 오히려 좋은 소식입니다. 벤더를 바꾸지 않고 당장 적용할 개선이 있다는 뜻이기 때문입니다. 지금 쓰는 LLM에 "이 티켓의 심각도를 판단해" 같은 넓은 질문 하나를 던지는 대신, 판단을 잘 정의된 작은 질문 여러 개로 쪼개고 결과를 코드에서 합치면 됩니다. 돈을 들이지 않고 얻는 가장 큰 개선이고, 해 두면 나중에 Jev로 옮기기도 쉬워집니다. 질문 집합이 이미 타입 형태로 존재하기 때문입니다.

확률 보정이라는 약한 고리

정해진 형식을 벗어나지 않는다는 점은 출력 후보를 형식에 맞게 강제하는 기존 기법(constrained decoding)으로도 이미 얻을 수 있고, 질문을 한꺼번에 처리하는 것은 좋은 공학이지만 새 범주를 만들 근거는 아닙니다. 남는 것은 확률 보정입니다. 90% 확신이라고 표시한 답이 실제로 90% 맞는다면 Jev는 JSON 모드 LLM 호출과 종류가 다른 도구이고, 아니라면 인터페이스를 잘 다듬은 빠르고 싼 분류기에 지나지 않습니다.

문제는 TypeSafe가 신뢰도 곡선도 보정 오차도 단 하나 공개하지 않았다는 점입니다. 그래서 증거가 전적으로 외부 측정에 달려 있는데, 그 결과가 나쁩니다. 구조화 출력 LLM 8종과 함께 측정한 독립 벤치마크에서 Jev의 보정 오차(ECE, expected calibration error)는 0.246으로 측정된 모든 시스템 중 가장 컸고, LLM들은 0.039~0.122 범위였습니다. 이 값은 표시한 확신과 실제 정답률이 얼마나 어긋나는지를 재며, 작을수록 좋습니다. 불확실할 수밖에 없도록 설계된 문항에서 LLM들이 97.3~100% 비율로 "모르겠다"를 인정한 반면 Jev는 49.7%만 인정했습니다.

다른 측정도 같은 방향입니다. Banking77에서 평균 표시 신뢰도 88%에 실제 정확도 약 80%로 체계적 과신이 관측되었고, 확신 값을 실제 정답률에 맞춰 사후에 눌러 주는 보정(temperature scaling)만으로 오차를 3분의 2까지 줄일 수 있었습니다. 학습 때 보지 못한 낯선 입력(out-of-distribution)을 다룬 연구에서는 예/아니오 답은 오히려 과소 확신인 반면 선택과 점수 답이 강하게 과신했고, 답이 원리적으로 불가능한 과제에서도 평균 확률 0.74를 부여했습니다.

반대 증거도 있습니다. 좁은 과제 집합에서는 틀린 답이 모두 낮은 신뢰도로 나왔다는 보고가 있고, 0.99 임계값 위에서는 정확도가 100%로 올라가며 그 구간이 트래픽의 60%를 덮는다는 측정도 있습니다. 종합하면 이렇습니다. 익숙한 입력에서는 보정이 대체로 작동하고 낯선 입력에서 무너집니다. 그리고 낯선 입력이야말로 엔지니어가 확신 값에 기대고 싶은 바로 그 구간입니다.

실무 지침은 하나로 모입니다. 신뢰도 값을 가공 없이 그대로 쓰지 마십시오. 자동 동작을 걸기 전에 자기 데이터로 정답을 붙인 표본을 만들어 확신 값을 실제 정답률에 맞춰 보정하십시오. 직관과 반대되는 관측도 하나 있습니다. 지시문을 더 정교하게 다듬었더니 보정 오차가 0.040에서 0.116으로 오히려 나빠졌다는 보고가 있으므로, 기준 문장을 고칠 때마다 보정을 다시 재야 합니다.

마지막으로 "환각 0%"는 위험 평가에 넣을 문장이 아닙니다. TypeSafe 스스로 이를 스키마 보장에 근거한 비경험적 수치라고 밝혔습니다. 스키마 밖 출력이 0이라는 뜻이지 오판이 0이라는 뜻이 아닙니다. 실제 정확도는 독립 측정 기준 76~80%대이고, Jev는 근거를 전혀 돌려주지 않으므로 오답이 나왔을 때 손에 쥐는 단서는 확률 분포 하나뿐입니다. 결과를 검증할 체계를 처음부터 비용에 넣어야 합니다.

인용하기 전에 알아야 할 것

창업자 이력은 과장되어 있습니다. 창업자 Diogo Almeida는 RLHF를 명령 수행 언어 모델에 적용해 ChatGPT의 기술 토대가 된 InstructGPT 논문의 주 저자 아홉 명 중 한 명이고 GPT-4 기술 보고서 공저자입니다. 그러나 RLHF 기법 자체를 제안한 2017년 논문의 저자는 아닙니다. 그는 RLHF를 언어 모델에 실용화하는 데 기여했지 기법을 창안하지 않았습니다. "ChatGPT 발명자"라는 헤드라인은 수십 명에게 똑같이 붙일 수 있는 표현입니다. 이 과장이 왜 생기는지도 짐작이 갑니다. 회사의 핵심 주장이 "RLHF가 망가졌다"는 것이라, 그가 RLHF를 만든 사람이라는 설명이 클수록 그 부정이 권위 있게 들립니다.

LangChain을 독립 검증으로 인용하면 안 됩니다. "LangChain이 Jev가 LLM 판정자보다 싸고 일관적임을 확인했다"는 식으로 널리 인용되지만, 해당 글을 실제로 확인하면 자체 평가를 전혀 수행하지 않았습니다. TypeSafe 자사 수치를 그대로 옮긴 공지 겸 안내 글이고, LangChain 본인도 소개된 사례를 "시연이지 검증된 벤치마크가 아니다"라고 밝히고 있습니다.

제품은 공개 7일 차입니다. 논문도 기술 보고서도 공개 가중치도 없습니다. 학습법에 붙은 이름은 있지만 손실 함수도 데이터 생성 절차도 공개된 것이 없어 기술적 장점을 평가할 방법 자체가 없습니다. 자체 호스팅도 파인튜닝도 없습니다. 4,000만 달러 시드를 받았는데 조사한 여섯 개 출처 어디에도 공동 투자자 이름이 하나도 나오지 않고, 보도된 기업가치는 회사가 확인해 주지 않았습니다.

실제 트래픽 위에서 Jev를 운영한다고 밝힌 이름 있는 기업은 아직 없습니다. 여러 플랫폼에 Jev 경로가 있지만 이들은 Jev를 쓸 수 있게 연결해 둔 벤더이지, 써 보니 괜찮더라고 알려 온 고객이 아닙니다. 커뮤니티 목록에 일주일 만에 150개 넘는 프로젝트가 올라왔지만 수치는 전부 저자 자기 보고이고 주말 실험과 실배포를 구분하지 않습니다.

한편 특정 벤더에 묶일 위험은 생각보다 작습니다. 인터페이스가 단순해서 일주일 만에 오픈소스 복제품이 여럿 나왔고, 일부는 코드를 고치지 않고 바꿔 끼울 수 있습니다. 정작 발이 묶이는 곳은 API가 아니라 확률 보정입니다. Jev의 확률 분포에 맞춰 임계값을 정해 두면 다른 모델로 옮길 때 그 임계값이 전부 틀어지므로, 이전 계획에는 재보정 비용을 반드시 넣어야 합니다.

결론

이번 조사에서 가장 값어치 있는 결과는 Jev에 대한 판정이 아니라 Jev가 우연히 드러낸 사실입니다. 판단을 타입 있는 질문으로 쪼개는 것은 모델과 무관하게 듣는 기법이고, TypeSafe 자신의 평가 표가 그 증거를 담고 있습니다. 지금 사내에서 LLM에 넓은 질문 하나를 던지고 있다면, 벤더를 바꾸기 전에 질문부터 쪼개는 것이 비용 없이 얻는 가장 큰 개선입니다.

Jev 자체에 대한 정직한 요약은 이렇습니다. 좋은 제품이지만 새로운 패러다임은 아니며, 범주를 정당화했을 유일한 속성인 확률 보정이 가장 나쁘게 측정됩니다. 남는 것은 질문을 한꺼번에 묶을 때의 비용 이점과, 선택지가 늘어도 응답 시간이 일정하다는 점입니다. 이 둘은 진짜 공학적 성취이지만, 앞서 적은 좁은 조건 안에서만 쓸모가 있습니다.

도입한다면 실제 트래픽을 흘려보내되 결과는 쓰지 않는 그림자 모드(shadow mode)로 먼저 돌려 보고, 자기 데이터로 신뢰도를 보정한 뒤에야 자동 동작을 걸고, 신뢰도 임계값을 안전 경계로 쓰지 말고 결정론적 검사와 나란히 두십시오. 지금 여러 기업이 실서비스에 쓰고 있다고 말하는 사람은 확인된 것보다 앞서 나간 것입니다. 일주일은 무엇도 증명하기에 짧고, 이 문서의 거의 모든 수치는 여섯 달 뒤 다시 확인해야 합니다.
